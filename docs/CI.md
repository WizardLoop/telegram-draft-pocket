# CI and the macOS handoff

No remote build, native test, or recording is implied by committing these workflows. Actual results belong in `docs/TESTING.md` and the workflow's uploaded `status.json`.

## Hosted runner verified on 2026-11-04

The standard `xcode-27` Apple Silicon runner is listed in [GitHub's hosted-runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). The published [runner image inventory](https://github.com/actions/runner-images/blob/main/images/macos/xcode-27-arm64-Readme.md), image `20261026.0314.1`, lists macOS 27.0.1, Xcode 27.1 (`27A9275`), and available iOS 27.0/27.1 runtimes. This matches the toolchain family locked in `Integration/BASE.json`; the job verifies its actual machine before doing a build. It never overrides the Xcode pin or silently substitutes another version.

GitHub lists the standard runner as 3 M1 CPUs, 7 GB RAM and 14 GB storage. These are documented runner specifications, not measurements of this project. A full Telegram build may exhaust memory, disk, or the 120-minute limit. Earlier attempts used 90 minutes; run `41949751852` reached approximately 89 minutes before its main step failed and the overall run ended cancelled. The longer ceiling leaves room for both native validation and capture; it does not remove their own startup/test timeouts. The preflight records actual free disk space; a build failure remains a failure. Exact pinned submodules use `--init --checkout --recursive --depth=1 --jobs=4`, with no `--remote`. Git fetches the recorded gitlink commits or fails; it never upgrades a dependency. Download output and stage names are streamed. History/disk savings are unmeasured, and dependencies already cloned with full history are not rewritten.

The published image inventory does not list FFmpeg. For a demo-enabled package, the toolchain stage checks `ffmpeg`/`ffprobe` and installs the Homebrew `ffmpeg` formula on the ephemeral runner if needed, before the native build. It records the actual media-tool versions. This does not alter the pinned app toolchain or purchase resources.

Standard hosted runners are free for public repositories according to the linked GitHub reference. This workflow refuses private repositories and never selects `-large`, `-xlarge`, or a paid/self-hosted runner. No workflow changes billing, repository visibility, Actions policy, secrets, or account settings. Artifact retention is one day. Account-specific artifact-storage allowances still need to be respected.

## Triggering a reviewed attempt

The macOS workflow is not triggered automatically by a push or ordinary PR update. A maintainer can explicitly apply `run-simulator` to a Draft PR whose head belongs to this same public repository. The `pull_request: labeled` event tests GitHub's PR merge ref, as described in [GitHub's event documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). Evidence records the feature head SHA separately from the tested merge SHA.

Concurrency is scoped to the ref and feature commit. Repeated requests for the same revision serialize, while a deliberately requested newer revision can run alongside the preceding attempt without cancelling its evidence. Avoid queueing redundant attempts; cancel a superseded pending request before replacing it.

`workflow_dispatch` is also defined, with a default-false usage acknowledgement. GitHub normally requires the workflow to exist on the default branch before manual dispatch is available. The label route allows the first reviewed attempt while implementation stays on `feature/draft-pocket`; do not push implementation to `main` or merge the PR just to expose the Run workflow button.

The workflow has two explicit lanes. `full-client` is the default dispatch choice and the `run-simulator` label selects it. The separate `editor` choice, or `run-editor-simulator` label on the same-repository PR, selects only the three legacy UIKit selection tests. It uses the same standard `xcode-27` runner, a 40-minute ceiling, read-only repository permission and one-day artifacts. It receives no Telegram build configuration or secret. Its runtime guard also refuses private, fork, unacknowledged dispatch and unrelated events. Concurrency includes the lane so this request does not cancel a full-client attempt.

The separate `verify.yml` runs packaging regression tests, feature-only clean reconstruction, feature-plus-demo clean reconstruction, exact repeated application, and demo application to a fully verified feature state. It uses actual pinned upstream checkouts for the integration checks. It is explicitly named **not iOS**. A green packaging job proves neither compilation nor behavior in Telegram.

The editor lane reconstructs the feature from the same pinned upstream commit, verifies the original SwiftPM manifests and their sole local `MosaicLayout` dependency, then uses the supported `RichTextEditor-Package` scheme and `RichTextEditorUIKitTests/DocumentTextSelectionTests` filter. It separates `build-for-testing` and `test-without-building` using [Apple's documented actions](https://developer.apple.com/library/archive/technotes/tn2339/_index.html), with one owned Simulator UUID and one fresh DerivedData directory. Compilation precedes boot. This isolated lane allows up to 300 seconds for boot, based on the measured startup delays in prior runs; the full-client lane's default remains 180 seconds. Build and test commands have separate 1,200/300-second bounds and cleanup runs after failure. No Bazel server or full Telegram build is needed for these three cases.

Its `draft-pocket-editor-RUN-ATTEMPT` artifact contains unfiltered command logs, toolchain/commit/patch identity, owned-device lifecycle evidence, exported native xcresult JSON and `native-cases.json`. A pass requires exactly the three named native cases with `Success`, no native errors, no crash/restart indicator and successful cleanup. A zero exit code or a zero-test run is insufficient. Native binaries, DerivedData and opaque xcresult diagnostics stay outside the upload directory. Download from the run's Artifacts section; inspect `status.json` first and then each native case. This lane does not launch Telegram or produce a demo movie.

## Owner-provided configuration

The macOS attempt expects an already configured `DRAFT_POCKET_BUILD_CONFIGURATION_JSON` repository secret. Start with [`Integration/build-configuration.example.json`](../Integration/build-configuration.example.json), replace the two API placeholders with the owner's `api_id` and `api_hash` from [my.telegram.org/apps](https://my.telegram.org/apps), and save the complete JSON as that Actions secret. Do not paste those values into the PR, chat, repository, or logs. The validator checks every required field before invoking the upstream build system.

`org.wizardloop.draftpocket` is the proposed local bundle namespace. `DRAFTLOCAL` is a **Simulator-only namespace marker**, not an Apple Developer team or credential. With provisioning and Simulator signing disabled, the code uses it only to form the application identifier; the example disables Siri and iCloud. An owner with an actual team can use their own ten-character team identifier instead. No paid Apple membership, certificate or distribution profile is required by this unsigned Simulator configuration. Runtime keychain/app-group behavior with the local marker remains unverified until the client is actually built and run. Never use the marker for a device/distribution build. This repository supplies no Telegram API credentials or copied upstream secrets.

The job writes the configuration only to the ephemeral runner's temporary directory, removes it from child-process environment variables, masks sensitive fields and redacts captured logs. Configuration files, app binaries, archives, account databases and build caches are excluded from uploaded artifacts. Missing or malformed configuration stops the attempt with an explicit error. Creating a secret or changing repository settings is a separate owner action.

The Simulator build uses the pinned upstream `Make.py` and its full `Telegram/Telegram` target. A narrow integration patch exposes its existing `--disableProvisioningProfiles` capability to `build` and `test`, forwards the Telegram build setting and disables Simulator bundle/framework signing through the pinned rules_apple feature. Device builds reject this option. The wrapper also passes `--xcodeManagedCodesigning` to satisfy the upstream configuration resolver; it does not import a certificate or retrieve a profile. Distribution signing is not part of the workflow. A flag accepted by project generation alone was insufficient at this base.

## Evidence and current capture boundary

`status.json` distinguishes package integrity, portable tests, toolchain, configuration, reconstruction, build, native tests and capture. Portable tests run on the actual Mac before dependency checkout and the full app build, so host-specific failures stop early. A stage that did not run stays `not_run`; an interrupted stage can remain `running`. Redacted logs and toolchain metadata are uploaded with an `always()` step when the runner can still execute it. Failure before runner allocation or forced job termination can prevent artifact upload and must not be reported as a successful attempt.

After a successful app build, full-client capture runs first, before independent native tests can leave a timed-out Simulator behind or consume the remaining recording time. A failed capture does not suppress native validation. Native targets are prebuilt before booting an explicitly owned device; test execution uses its exact UUID, with synchronous owned-device cleanup. Both outcomes and their failure details remain in the evidence; the workflow exits unsuccessfully if either native validation or capture fails. A failed app build prevents both dependent stages.

The optional demo now has source for an isolated fictional `@wizardloop` account in the full Telegram client, with a real XCTest target. It remains unvalidated until an actual native run passes. `export-demo` seals its separate patch and overlay only after exact feature input hashes and ordered application pass. Build and test use `--with-demo` when this section is available; the normal feature remains separately reconstructable. An unavailable demo still stops capture explicitly.

After a native fix, `export --invalidate-demo` explicitly re-exports the feature and invalidates only generated demo manifest state, retaining authored fixture sources and `demo.patch`. Default export refuses to overwrite an available demo. Refresh any changed demo inputs, run `export-demo --reference /path/to/feature-checkout`, and repeat reconstruction before using the demo. Native test registrations may include an explicit XCTest class filter so shared test libraries do not run unrelated suites.

`scripts/capture-demo.py` first builds the exact XCTest target with the same test configuration, without executing it. It then creates a new iPhone 17 / iOS 27.0 Simulator and records that exact UDID using `simctl io recordVideo`. The pinned public rules_apple destination argument directs XCTest to the same device. Story and QA run as separate continuous takes, using native XCTest filters; test-result caching is disabled. Recorder readiness, full-run continuity, the exact successful native test case, and ordered action markers within the take are checked. Partial recordings and logs survive failures. Startup, build and test behavior still require actual Mac validation.

The shared lifecycle helper records bounded boot phases, device counts and the owned device state, disk space, memory/swap information and selected process memory without command arguments. Process names include the actual Bazel server and Swift worker names, not just Java. A framebuffer screenshot must decode to nonblank pixels before recording. Recorder output goes directly to a file; a live recorder must emit its native readiness message within 30 seconds. The helper does not infer readiness from a file appearing. If Apple's documented `FramebufferServerRendererPolicy=none` is present, it may temporarily remove only that preference on a verified GitHub-hosted runner with artifacts under `RUNNER_TEMP`, then restore it during cleanup. Local host preferences are never changed. Diagnostic write failures cannot prevent attempted owned-device shutdown/delete or preference restoration.

Run `41992720504` showed severe memory pressure during a failed boot, without proving which process caused it. After each capture/native build-only batch, the helper now attempts to release that task's Bazel server before creating its Simulator, following [Bazel's script/server guidance](https://bazel.build/run/scripts#notes-about-server-mode). This is restricted to GitHub-hosted jobs whose checkout and evidence directory resolve inside `RUNNER_TEMP`. It verifies the exact pinned Make binary and the server's workspace/output base against the completed build's output link, then uses a bounded `shutdown` with `--noblock_for_lock`. A busy server or identity mismatch stops the stage with evidence; it never kills global processes or cleans build outputs/cache. Before/after resource snapshots are retained. Local and self-hosted runs skip this operation. The subsequent test command starts a server again; whether this reduces pressure enough for boot and recording remains to be measured on CI. No JVM heap cap or Simulator GUI workaround is assumed necessary.

Native tests pin their own device/runtime in `BASE.json` independently of the optional demo. All targets are compiled before device boot. Runtime tests share the newly created explicit UUID; a failed target triggers an owned-device restart before the next target. `--artifacts /path/to/evidence` preserves lifecycle and per-target build/test results for manual native runs. The explicit UUID also enables full test output, so successful test logs are retained. Neither the native lane nor capture uses a global shared simulator or shuts down an unrelated device.

Artifacts include raw MOV takes, action timestamps emitted around real UI actions, redacted native xcresult JSON, patch/commit identity, FFprobe stream/frame metadata, decoded frame-change measurements and neighboring frames during Put Aside/Restore/Delete/Undo. The pinned [xctestrunner](https://github.com/google/xctestrunner/blob/4c6f4931aa65b3e6573b3ca11753c98fc8d3071c/xctestrunner/test_runner/xctest_session.py) writes `test.xcresult` into Bazel's undeclared test outputs. The driver safely copies/extracts that bundle, queries the same legacy native schema as the pinned runner, and requires exactly the requested case with `Success`. Bazel's generic wrapper XML is ancillary evidence; its one synthetic testcase cannot prove which XCTest ran. Native bundle file hashes are retained, but opaque binary diagnostics are not uploaded because they cannot be reliably redacted.

The driver also exports only the explicitly named XCTest screenshots: composer before Put Aside, composer after Restore, both local enqueue moments, Delete/Undo, and restored composer after relaunch. It follows the successful case's native summary and uses Apple's documented [object export command](https://developer.apple.com/documentation/xcode-release-notes/xcode-16_3-release-notes) for those PNG/JPEG payloads. Expected counts, native payload sizes, image decoding and fixed safe output names are checked before publishing `screenshots/`; its manifest records the native case/reference, timestamp, dimensions and SHA-256. Other attachments and activity diagnostics are not exported. These images preserve evidence for visual formatting review; their existence alone does not prove formatting survived.

The pinned runner generates `UserAttachmentLifetime = keepNever`. The optional demo applies a one-field patch to the same `0.2.16-20260212-4c6f493` dependency, using Bazel's supported [transitive module override](https://bazel.build/versions/9.0.0/external/module#overrides), to retain custom attachments. Automatic system screenshots remain disabled. Exact patch application against the pinned source passed; actual attachment retention still requires the native run.

After building the test target, the capture driver reads its generated runner's literal `TEST_HOST_PATH` and resolves that exact artifact through the target's Bazel runfiles manifest. This follows the iOS configuration transition; it does not assume the host-configured `bazel-bin` contains the app or search old output folders. The driver hashes the selected IPA's main executable and TelegramUI/TelegramCore framework executables, together with their bundle metadata. After XCTest it queries the dedicated Simulator's installed app container and requires those six files to match. System path aliases such as `/var` and `/private/var` are normalized at the trusted root; links or escapes within the device are rejected. Artifacts contain only hash inventories and relative build identity, never app binaries or build configuration. Missing or mismatched installed binaries fail capture verification.

The decoder inspects every captured frame at reduced luma resolution; action windows are aligned approximately using test UTC timestamps and recorder readiness. Duplicate presentation timestamps are counted explicitly. Review the native frames and raw take before claiming appearance or animation quality. An encoded frame rate, even 60 fps, is not proof of 60 distinct UI updates. No synthetic frames, speed-up, silent timing fix, or mock success video is generated. The requested 1920×1920, approximately 36-second production export remains a separate review/editing step after real capture exists.

For manual launch, `bash Demo/run-demo.sh --app /path/to/Telegram.app` verifies the debug-only demo marker in executable code, Simulator Mach-O platform, package and Xcode pin before creating a fresh dedicated device. Optional `--udid` reuse requires matching launcher-saved UUID/name/runtime/bundle identity; an arbitrary existing Simulator is rejected. It never erases accounts or uninstalls apps. A successful launch request is not a passing runtime test.

## Local Mac fallback

Only consider a local or separately authorized Mac after reviewing the hosted attempt. The required environment is Apple Silicon, macOS 27, Xcode 27.1, Python 3, Git, the exact pinned submodules and the owner's development configuration. A working provisioning/signing account is not required for an unsigned Simulator build.

For planning, 16 GB RAM and 100 GB free disk are conservative engineering suggestions, **not measured minimum requirements or a tested purchase recommendation**. The actual full-client build, native tests, runtime QA and capture must determine whether the available Mac is sufficient. Do not purchase or provision a paid machine automatically.

Use a new checkout and a dedicated Simulator. Reconstruct with `scripts/check-integration.sh`, then run `scripts/build-simulator.sh` and `scripts/test.sh --native` with the documented local configuration and cache arguments. Add `--with-demo` consistently when testing the optional fixture. Keep build numbers distinct and install only the latest verified `.ipa` payload; the upstream `Telegram_archive-root` directory can be stale. Use the capture driver for continuous raw takes and timestamped-frame inspection, and report measured frame pacing separately from the final export's nominal 60 fps.
